## Modules and triggers

Blue's CSS is split into **modules**: `button`, `forms`, `table`, `dialog`, `tabs`… Each declares the tokens that pull it in:

```js
{ id: 'dialog', file: 'dialog.css', layer: 'components',
  triggers: ['tag:dialog', 'attr:role=dialog', 'attr:role=alertdialog'],
  deps: ['motion'] }
```

| Token | Matches |
|---|---|
| `tag:<name>` | an element, e.g. `tag:table` |
| `attr:<name>` | an attribute with any value, e.g. `attr:popover` |
| `attr:<name>=<value>` | a literal value, e.g. `attr:role=tab` |
| `text:<literal>` | a library marker, e.g. a CSS variable a component writes inline |

`tokens`, `reset` and `base` always ship. Everything else ships only when the output contains one of its triggers. The full list is on [Modules](/reference/modules).

## Scanning what you ship

The scanner reads **build output**, not your source: HTML, every JS chunk, JSON payloads. Compiled framework code keeps tag names and literal attributes as strings:

```js
_createElementVNode("dialog", …)   jsx("table", …)   { role: "tab", "data-badge": "" }
```

That includes what libraries in `node_modules` render — reka-ui's `role: "tab"` shows up in your bundle, so Blue knows your app has tabs.

- **False positives** (the word `"table"` in some string) cost a few bytes.
- **False negatives** are the bug to avoid: `v-html`, CMS or markdown content, `<component :is>`, fully dynamic attributes. Cover those with a `safelist`, and let the doctor find them.

## The doctor

[`blue-css doctor`](/integrations/doctor) renders your pages in a headless browser and compares the live DOM with what each page's stylesheet shipped — every Blue build declares its modules in a `--blue-modules` custom property. It exits non-zero when an element's styles were shaken away, so it can gate CI.
